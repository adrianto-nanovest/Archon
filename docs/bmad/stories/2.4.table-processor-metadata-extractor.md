# Story 2.4: Table Processor & Metadata Extractor (Enhanced with Docling Metadata)

## Status
Done

## Story

**As a** backend developer,
**I want** to implement hierarchical table conversion, 3-tier JIRA metadata aggregation, and rich attachment metadata extraction,
**so that** complex Confluence tables are RAG-optimized, JIRA coverage reaches ~100%, and attachment metadata enriches search capabilities.

## Acceptance Criteria

1. **Table Processor** (~350 lines):
   - **CRITICAL**: Use hierarchical markdown format (NOT standard markdown tables)
   - Convert to `## Row` → `### Column` structure
   - Wrap with `<!-- TABLE_START -->` and `<!-- TABLE_END -->` markers
   - Add table summary comment: `<!-- Table Summary: {cols} columns, {rows} rows, ... -->`
   - Handle colspan/rowspan with content duplication (fill all spanned cells)
   - Build multi-level header matrix (rowspan + colspan in headers)
   - Calculate context-aware heading levels (detect surrounding section level)
   - Add metadata enrichment: table complexity score, purpose inference, span locations

2. **Metadata Extractor with Docling Enrichment** (~200 lines):
   - Aggregate JIRA links from all 3 tiers (macros + URLs + regex)
   - Deduplicate user mentions by account ID
   - Deduplicate internal/external links by URL
   - Deduplicate asset links by filename
   - Calculate content metrics: word_count, content_length
   - **Extract rich attachment metadata from Docling-processed documents:**
     - **page_count** (PDF/DOCX documents)
     - **table_count** (tables found in attachments)
     - **code_block_count** (code snippets in attachments)
     - **image_count** (images in attachments)
     - **has_formulas** (mathematical content detection)
     - **document_structure** (sections, headings, TOC presence)
   - **Store attachment metadata in `asset_links` array with `processed=true` flag**
   - Build metadata dict matching `confluence_pages.metadata` JSONB schema

### Architecture Context: Hierarchical Table Format (CRITICAL)

**Source:** [docs/bmad/brownfield-prd/epic-2-html-to-markdown-content-processing.md](docs/bmad/brownfield-prd/epic-2-html-to-markdown-content-processing.md#347-hierarchical-tables-not-standard-markdown-tables)

**Rationale:** Standard markdown tables have critical limitations for Confluence content:
- **No colspan/rowspan**: 35% of Confluence tables have spans
- **No nested content**: 60% have code blocks, lists, formatting inside cells
- **No multi-level headers**: 20% have rowspan in headers
- **Poor RAG performance**: Flat structure loses context across chunk boundaries

**Hierarchical Format Benefits:**
- ✅ Preserves all content (colspan/rowspan via content duplication)
- ✅ Supports nested structures (code blocks, lists remain intact)
- ✅ Semantic sections (each row is a searchable unit)
- ✅ Metadata enrichment (table complexity, purpose, structure in comments)
- ✅ **10x better RAG retrieval** vs. standard markdown tables

**Example Hierarchical Output:**

```markdown
<!-- TABLE_START -->
<!-- Table Summary: 3 columns, 4 rows, complexity: 0.15, purpose: data, spans: 2 -->

## Row 1 (Header Row)
### Column 1: Product Name
Product Name

### Column 2: Price
Price

### Column 3: Status
Status

## Row 2
### Column 1: Product Name
Widget A

### Column 2: Price
$19.99

### Column 3: Status
In Stock

## Row 3
### Column 1: Product Name
Widget B

### Column 2: Price
$29.99

### Column 3: Status
Out of Stock

<!-- TABLE_END -->
```

**Context-Aware Heading Levels:**
- If table inside `<h2>` section → use `####` (level 4) for rows, `#####` (level 5) for columns
- If table at document root → use `##` (level 2) for rows, `###` (level 3) for columns
- Algorithm: `base_level = surrounding_heading_level + 2`

### Architecture Context: 3-Tier JIRA Extraction Strategy (CRITICAL)

**Source:** [docs/bmad/brownfield-prd/epic-2-html-to-markdown-content-processing.md](docs/bmad/brownfield-prd/epic-2-html-to-markdown-content-processing.md#328-three-tier-jira-extraction-critical)

**Problem:** Regex-only extraction achieves only ~40% coverage → **UNACCEPTABLE**

**Solution:** Three-tier extraction strategy

**Tier 1: Confluence JIRA Macros** (~40% coverage) - **Story 2.2 ✓**
- Source: `<ac:parameter ac:name="key">PROJ-123</ac:parameter>`
- Accuracy: 100% (explicit Confluence embedding)
- Implemented in: `python/src/server/services/confluence/macro_handlers/jira_macro.py`

**Tier 2: JIRA URLs in Hyperlinks** (~30% coverage) - **Story 2.3 ✓**
- Source: `<a href="https://jira.../browse/PROJ-123">`
- Pattern: `https?://[^/]+/browse/([A-Z]+-\d+)`
- Implemented in: `python/src/server/services/confluence/element_handlers/link_handler.py`

**Tier 3: Plain Text Regex Fallback** (~30% coverage) - **Story 2.4 (This Story)**
- Source: "See PROJ-123 for details" in text content
- Pattern: `\b([A-Z]+-\d+)\b` (word boundaries prevent false positives)
- Run AFTER markdown conversion (on final markdown content)
- Implementation: `python/src/server/services/confluence/metadata_extractor.py:_extract_jira_from_plain_text()`

**Deduplication Strategy:**
- Each tier adds to shared `jira_links_tracker`
- Tier 2 checks tracker before adding (Story 2.3)
- Tier 3 checks tracker before adding (Story 2.4)
- Final metadata extractor deduplicates by `issue_key`

**Impact:** ~100% JIRA coverage vs. 40% regex-only → **CRITICAL for JIRA-integrated Confluence spaces**

### Architecture Context: Colspan/Rowspan Handling Pattern

**Source:** [docs/bmad/confluence-html-processing-analysis.md](docs/bmad/confluence-html-processing-analysis.md#4-table-processing---hierarchical-strategy)

**Production Code Reference:** Lines 1176-1936 in `enhanced_renderer_sample.py`

**Pattern:** Content duplication across spanned cells

**Colspan Example:**
```html
<table>
  <tr>
    <td colspan="3">Merged Header</td>
  </tr>
  <tr>
    <td>Cell 1</td>
    <td>Cell 2</td>
    <td>Cell 3</td>
  </tr>
</table>
```

**Hierarchical Output:**
```markdown
## Row 1
### Column 1: Merged Header
Merged Header

### Column 2: Merged Header
Merged Header

### Column 3: Merged Header
Merged Header

## Row 2
### Column 1
Cell 1

### Column 2
Cell 2

### Column 3
Cell 3
```

**Rowspan Example:**
```html
<table>
  <tr>
    <td rowspan="2">Spanned Cell</td>
    <td>Cell A</td>
  </tr>
  <tr>
    <td>Cell B</td>
  </tr>
</table>
```

**Hierarchical Output:**
```markdown
## Row 1
### Column 1: Spanned Cell
Spanned Cell

### Column 2
Cell A

## Row 2
### Column 1: Spanned Cell
Spanned Cell

### Column 2
Cell B
```

**Algorithm:**
1. Build cell matrix with span tracking
2. For each spanned cell:
   - Duplicate content to all spanned positions
   - Mark duplicated cells with metadata
3. Generate hierarchical markdown from filled matrix

async def html_to_markdown(self, html: str, page_id: str, space_id: str = None):

    await self._process_macros(soup, page_id, space_id)
