**As a** backend developer,
**I want** to create `ConfluenceSyncService` with CQL-based incremental sync logic,

#### CQL-Based Incremental Sync Strategy

**Why CQL?**
- **No full space scans**: Only fetch changed pages via `lastModified >= "{timestamp}"`
- **Efficient**: Minimize API calls (Confluence Cloud rate limits: 10 req/sec)
- **Fast**: Sub-second query execution for spaces with 1000+ pages

**CQL Query Pattern:**
```python
cql_query = f'space = {space_key} AND lastModified >= "{last_sync_timestamp}"'
changed_pages = confluence_client.cql_search(cql_query, expand='body.storage,version,ancestors')
```

**CQL Search Expansion Parameters:**
- `body.storage`: Raw HTML content for processing
- `version`: Page version number for change detection
- `ancestors`: Parent page hierarchy for materialized path

**Deletion Detection Integration:**
- Story 3.1 handles version-based detection (pages in CQL results)
- Story 3.3 will add full deletion reconciliation strategies

**Atomic Chunk Updates Integration:**
- Story 3.1 deletes old chunks before inserting new ones (simple strategy)
- Story 3.2 will add zero-downtime atomic updates with `_pending_deletion` flag

**Reference:** [CQL Documentation](https://developer.atlassian.com/cloud/confluence/cql/) for advanced query patterns

### Technical Constraints and Design Decisions

**Why Delete Old Chunks Before Inserting New Ones?**
- Story 3.1 uses **simple delete-then-insert strategy** for MVP speed
- Story 3.2 will implement **zero-downtime atomic updates** with `_pending_deletion` flag
- Trade-off: Brief search gap (milliseconds) acceptable for MVP

**Why Store last_sync_timestamp in archon_sources.metadata?**
- JSONB field allows flexible metadata without schema migrations
- Consistent pattern with other source types (web, upload)
- Easy to query: `metadata->>'last_sync_timestamp'`

**Why Track api_calls_made?**
- Confluence Cloud rate limits: 10 requests/second
- Observability: Detect if sync is hitting rate limits
- Future: Implement adaptive rate limiting based on metrics

**Why Use MaterializedPath for Hierarchy?**
- Efficient ancestor/descendant queries with single LIKE statement
- No recursive CTEs needed for breadcrumb generation
- Pattern: `/parent_id/child_id/grandchild_id`
