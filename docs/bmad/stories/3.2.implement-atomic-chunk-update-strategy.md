# Story 3.2: Implement Atomic Chunk Update Strategy

## Status
Draft

## Story

**As a** backend developer,
**I want** to implement zero-downtime chunk replacement with atomic updates,
**so that** Confluence content remains searchable during sync updates without gaps.

## Acceptance Criteria

1. Before inserting new chunks: mark old chunks with `metadata->>'_pending_deletion' = 'true'`
2. Insert new chunks from updated page content (via document_storage_service)
3. Delete old chunks WHERE `metadata->>'_pending_deletion' = 'true'` only after new chunks committed
4. Use database transaction to ensure atomicity (all or nothing)
5. On sync failure: rollback marks old chunks as active again (remove _pending_deletion flag)
6. Search queries exclude chunks with `_pending_deletion = 'true'` if new chunks available

    async def _update_page_chunks_atomic(
        self,
        page_id: str,
        markdown: str,
        page_url: str,
        source_id: str,
        progress_tracker: ProgressTracker | None = None
    ) -> None:
        """
        Update page chunks with atomic transaction.

        Ensures zero-downtime: Old chunks remain searchable until new ones committed.
        Rollback on failure preserves old chunks.
        """
        try:
            # STEP 1: Mark old chunks pending deletion (still searchable)
            await self._mark_chunks_pending_deletion(page_id)

            # STEP 2: Insert new chunks via document_storage_service
            await self.document_storage_service.add_documents_to_supabase(
                documents=[{"url": page_url, "content": markdown, "metadata": {"page_id": page_id}}],
                source_id=source_id,
                progress_tracker=progress_tracker
            )

            # STEP 3: Delete old chunks (only after new chunks committed)
            await self._delete_pending_chunks(page_id)

        except Exception as e:
            # ROLLBACK: Remove pending deletion flag, restore old chunks
            await self._rollback_pending_deletion(page_id)
            logger.error(
                f"Atomic chunk update failed for page {page_id}, rolled back pending deletion",
                exc_info=True
            )
            raise
    ```

        Delete chunks marked with _pending_deletion flag.

        Returns: Number of chunks deleted

        result = await self.supabase_client.from_("archon_crawled_pages").delete().eq(

        ).filter(
            "metadata->>page_id", "eq", page_id
        ).filter(
            "metadata->>'_pending_deletion'", "eq", "true"
        ).execute()

        deleted_count = len(result.data) if result.data else 0
        logger.info(f"Deleted {deleted_count} pending chunks for page {page_id}")
        return deleted_count

    async def _rollback_pending_deletion(self, page_id: str) -> int:
        """
        Rollback pending deletion by removing _pending_deletion flag.

        Restores old chunks to searchable state on failure.

        Returns: Number of chunks restored
        """
        result = await self.supabase_client.from_("archon_crawled_pages").update({
            "metadata": {
                **"metadata",  # Preserve existing metadata
                "_pending_deletion": None  # Remove flag

            "metadata->>page_id", "eq", page_id

            "metadata->>'_pending_deletion'", "eq", "true"
        ).execute()

        restored_count = len(result.data) if result.data else 0
        logger.info(f"Rolled back {restored_count} chunks for page {page_id}")
        return restored_count
    ```

#### Atomic Chunk Update Strategy

**Problem:** Simple delete-then-insert strategy (Story 3.1) creates brief search gaps (milliseconds) where page has zero searchable chunks.

**Solution:** Three-phase atomic update with `_pending_deletion` flag:

**Phase 1: Mark Old Chunks (No Impact on Search)**
```sql
UPDATE archon_crawled_pages
SET metadata = jsonb_set(metadata, '{_pending_deletion}', 'true')
WHERE metadata->>'page_id' = $1
  AND source_id = $2;
```
- Old chunks remain searchable (search excludes pending deletion chunks ONLY if new chunks exist)
- Zero downtime maintained

**Phase 2: Insert New Chunks**
```python
await document_storage_service.add_documents_to_supabase(
    documents=[{"url": page_url, "content": markdown, "metadata": {"page_id": page_id}}],
    source_id=source_id
)
```
- New chunks inserted
- Old chunks (with pending deletion flag) still exist
- **Both old and new chunks in database** (search returns old until new committed)

**Phase 3: Delete Old Chunks (After Success)**
```sql
DELETE FROM archon_crawled_pages
WHERE metadata->>'page_id' = $1
  AND metadata->>'_pending_deletion' = 'true';
```
- Old chunks removed
- Only new chunks remain
- Search automatically switches to new chunks

**Rollback on Failure:**
```sql
UPDATE archon_crawled_pages
SET metadata = metadata - '_pending_deletion'
WHERE metadata->>'page_id' = $1
  AND metadata->>'_pending_deletion' = 'true';
```
- Removes pending deletion flag
- Old chunks restored to active state
- Content remains searchable

**Search Query Modification:**
```sql
SELECT * FROM archon_crawled_pages
WHERE metadata->>'_pending_deletion' IS NULL  -- Exclude pending deletion chunks
  AND embedding <-> $1 < 0.8;  -- Vector similarity
```

**Why This Works:**
- **Zero Downtime**: Old chunks searchable until new chunks committed
- **Atomic**: Transaction ensures all-or-nothing (success = new chunks, failure = old chunks)
- **Safe Rollback**: Failure preserves old chunks (no data loss)
- **Simple Search Logic**: Single filter excludes pending deletion chunks

### Technical Constraints and Design Decisions

**Why Use `_pending_deletion` Flag Instead of Separate Table?**
- **Simplicity**: No schema migration needed (JSONB metadata is flexible)
- **Transient State**: Flag exists only during transaction (milliseconds)
- **No Cleanup**: Flag removed automatically on success or rollback
- **Performance**: Single JSONB field update (no JOIN needed)

**Why Not Use Database Transactions (BEGIN/COMMIT/ROLLBACK)?**
- **Supabase PostgREST Limitation**: Supabase SDK doesn't expose transaction control directly
- **Alternative**: Application-level atomic pattern with flag-based rollback
- **Trade-off**: Slightly more complex but works with Supabase SDK

**Why Exclude Pending Deletion Chunks from Search?**
- **Zero Downtime**: Ensures old chunks searchable until new chunks committed
- **Clean Results**: Prevents users seeing duplicate content (old + new chunks)
- **Simple Filter**: Single WHERE clause in search query

**Why Not Use Two-Phase Commit (2PC)?**
- **Overkill**: Single database (Supabase), no distributed transactions needed
- **Complexity**: 2PC adds coordinator overhead and failure scenarios
- **Sufficient**: Flag-based atomic pattern meets zero-downtime requirement

**Performance Impact:**
- **Mark Pending Deletion**: ~5ms (single UPDATE query)
- **Insert New Chunks**: ~50-200ms (depends on chunk count and embedding provider)
- **Delete Old Chunks**: ~5ms (single DELETE query)
- **Total Overhead**: ~10ms vs simple delete-then-insert (acceptable for zero-downtime guarantee)
