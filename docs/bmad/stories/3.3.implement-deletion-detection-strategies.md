# Story 3.3: Implement Deletion Detection Strategies

## Status
Done

## Story

**As a** backend developer,
**I want** to support configurable deletion detection strategies (weekly, every sync, on-demand),
**so that** deleted Confluence pages are removed from RAG system without excessive API calls.

## Acceptance Criteria

1. Strategy stored in `archon_sources.metadata->>'deletion_strategy'`: "weekly_reconciliation", "every_sync", "on_demand"
2. **weekly_reconciliation**: Check for deletions once per week (default), store `last_deletion_check` timestamp
3. **every_sync**: Call `get_space_pages_ids()` after each sync, compare with database page_id list
4. **on_demand**: Never check during sync (user manually triggers or notices 404s)
5. Mark deleted pages with `is_deleted = true` in confluence_pages, CASCADE delete chunks
6. Log deletion events with page_id, title, deletion_timestamp

    ```python
    async def _mark_pages_deleted(self, page_ids: list[str], source_id: str) -> int:
        """Mark pages as deleted and remove their chunks."""
        deleted_count = 0
        for page_id in page_ids:
            try:
                # Mark page as deleted
                await self.supabase_client.from_("confluence_pages").update({
                    "is_deleted": True,
                    "updated_at": datetime.now(UTC).isoformat()
                }).eq("page_id", page_id).execute()

                # Delete chunks (CASCADE delete via metadata->>'page_id')
                await self.supabase_client.from_("archon_crawled_pages").delete().eq(
                    "source_id", source_id
                ).filter("metadata->>'page_id'", "eq", page_id).execute()

                deleted_count += 1
                logger.info(f"Marked page {page_id} as deleted, removed chunks")
            except Exception as e:
                logger.error(f"Failed to delete page {page_id}: {e}", exc_info=True)
                # Continue with other pages (don't fail entire batch)
        return deleted_count
    ```

#### Deletion Detection Strategies

**Problem:** CQL-based incremental sync only detects modified pages. Pages deleted in Confluence are not returned by CQL queries, leaving orphaned data in RAG system.

**Solution:** Three configurable strategies to balance API efficiency vs. data freshness:

**Strategy 1: Weekly Reconciliation (Default)**
```python
# Check for deletions once per week
if last_deletion_check is None or (now - last_deletion_check).days >= 7:
    # Fetch all page IDs from Confluence
    api_page_ids = await confluence_client.get_space_pages_ids(space_key)
    # Compare with database page IDs
    db_page_ids = await self._get_db_page_ids(source_id)
    deleted_ids = db_page_ids - set(api_page_ids)
    # Mark deleted pages
    await self._mark_pages_deleted(deleted_ids, source_id)
    # Update last_deletion_check
    await self._update_last_deletion_check(source_id)
```
- **Pros**: Minimizes API calls (1 call per space per week)
- **Cons**: Deleted pages remain searchable for up to 7 days
- **Best for**: Large spaces (1000+ pages) where API efficiency matters

**Strategy 2: Every Sync**
```python
# Check for deletions after every sync
api_page_ids = await confluence_client.get_space_pages_ids(space_key)
db_page_ids = await self._get_db_page_ids(source_id)
deleted_ids = db_page_ids - set(api_page_ids)
await self._mark_pages_deleted(deleted_ids, source_id)
```
- **Pros**: Immediate deletion detection (within 1 sync cycle)
- **Cons**: Additional API call per sync (~10ms for spaces < 1000 pages)
- **Best for**: Small/medium spaces where data freshness is critical

**Strategy 3: On-Demand**
```python
# Never auto-check, only via manual trigger
if strategy == DeletionStrategy.ON_DEMAND:
    logger.debug("Skipping deletion detection (on_demand strategy)")
    # User calls check_deletions_on_demand() separately
```
- **Pros**: Zero API overhead during syncs
- **Cons**: Deleted pages remain until manual cleanup
- **Best for**: Spaces with rare deletions or manual curation workflows

### Technical Constraints and Design Decisions

**Why Three Strategies Instead of One?**
- **Flexibility**: Different spaces have different deletion patterns
- **API Efficiency**: Large spaces (4000+ pages) benefit from weekly checks
- **Data Freshness**: Critical spaces need immediate deletion detection
- **User Control**: Some users prefer manual curation (on_demand)

**Why Use `get_space_pages_ids()` for Detection?**
- **Lightweight**: Fetches only page IDs (no content, no metadata)
- **Already Implemented**: Story 1.2 added this method to ConfluenceClient
- **Fast**: Single API call returns all page IDs for comparison
- **Set Comparison**: O(n) deletion detection via set difference

**Why Not Use CQL for Deletion Detection?**
- **CQL Limitation**: Cannot query "pages that existed before but don't exist now"
- **Deletion Not Tracked**: Confluence doesn't expose deletion timestamps via CQL
- **Full Page List Required**: Must compare current API state with DB state

**Why Store `last_deletion_check` Separately?**
- **Independent from Sync**: Deletion check can run at different frequency than sync
- **Weekly Strategy**: Needs separate timestamp to enforce 7-day interval
- **On-Demand**: Allows manual triggering without affecting sync workflow

**Why Mark `is_deleted = TRUE` Instead of Hard Delete?**
- **Audit Trail**: Preserves record of what was in space
- **Restore Capability**: Future feature could restore deleted pages from DB
- **Simpler Implementation**: Avoids foreign key complexity with CASCADE delete

**Performance Impact:**
- **Weekly Strategy**: 1 extra API call per week (~10ms per 1000 pages)
- **Every Sync Strategy**: 1 extra API call per sync (~10ms per 1000 pages)
- **Chunk Deletion**: O(n) where n = chunks per page (~5ms per page)
