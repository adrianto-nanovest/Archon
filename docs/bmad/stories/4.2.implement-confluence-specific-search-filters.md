## Story

**As a** backend developer,
**I want** to add filter parameters to search API for space, JIRA, hierarchy, and mentions,
**so that** users can narrow search results using Confluence metadata.

## Acceptance Criteria

1. Modify `POST /api/knowledge/search` request schema to accept filters: space_key, jira_issue, hierarchy_path, mentioned_user
2. Add WHERE clauses: `confluence_pages.space_key = $1` (space filter)
3. JSONB containment: `confluence_pages.metadata->'jira_issue_links' @> '[{"issue_key": "PROJ-123"}]'` (JIRA filter)
4. Path prefix match: `confluence_pages.path LIKE '/parent_id/%'` (hierarchy filter)
5. User mention JSONB: `confluence_pages.metadata->'user_mentions' @> '[{"account_id": "..."}]'`
6. Combine filters with AND logic (all specified filters must match)

  - [x] Create method `_apply_confluence_filters()` in `HybridSearchStrategy`:
    ```python
    async def _apply_confluence_filters(
        self,
        results: list[dict[str, Any]],
        filters: ConfluenceSearchFilters,
    ) -> list[dict[str, Any]]:
        """
        Apply Confluence-specific filters to search results.

        Strategy: Post-filter results after enrichment (simpler than modifying SQL)
        - Space filter: exact match on space_key
        - JIRA filter: check jira_issue_links array contains issue_key
        - Hierarchy filter: path prefix match
        - User mention filter: check user_mentions array contains account_id

        All filters combined with AND logic.
        """
        if not filters:
            return results

        filtered_results = []
        for result in results:
            confluence_meta = result.get("confluence_metadata")

            # Non-Confluence chunks pass through if no filters are active
            if confluence_meta is None:
                # Exclude non-Confluence results when any Confluence filter is active
                if any([filters.space_key, filters.jira_issue,
                        filters.hierarchy_path, filters.mentioned_user]):
                    continue
                filtered_results.append(result)
                continue

            # Apply space_key filter (AC: 2)
            if filters.space_key:
                if confluence_meta.get("space_key") != filters.space_key:
                    continue

            # Apply jira_issue filter (AC: 3)
            if filters.jira_issue:
                jira_links = confluence_meta.get("jira_issue_links", [])
                if not any(link.get("issue_key") == filters.jira_issue for link in jira_links):
                    continue

            # Apply hierarchy_path filter (AC: 4)
            if filters.hierarchy_path:
                page_path = confluence_meta.get("path", "")
                if not page_path.startswith(filters.hierarchy_path):
                    continue

            # Apply mentioned_user filter (AC: 5)
            if filters.mentioned_user:
                user_mentions = confluence_meta.get("user_mentions", [])
                if not any(m.get("account_id") == filters.mentioned_user for m in user_mentions):
                    continue

            filtered_results.append(result)

        return filtered_results
    ```

### Technical Design Decisions

**Why Post-Filter Instead of Database Query Modification?**
- **Simpler implementation**: Filters operate on already-enriched results
- **Consistent with Story 4.1**: Story 4.1 chose post-processing over SQL function changes
- **Easier testing**: Filter logic can be unit tested with mock data
- **Performance acceptable**: Filtering in-memory is fast for typical result sizes (10-50 results)
- **Future optimization**: If performance becomes an issue, filters can be pushed to database in Story 4.3

**Why Exclude Non-Confluence Chunks When Filters Active?**
- Filters like `space_key` or `jira_issue` are Confluence-specific
- Including web crawl results when user explicitly filters by space would be confusing
- Clear UX: "Show me DEVDOCS space results" means only Confluence results from that space

**Filter Combination with AND Logic:**
- Matches user expectation: "space=DEVDOCS AND jira=PROJ-123" narrows results
- OR logic would require more complex UI to express
- Can add OR support in future if needed
