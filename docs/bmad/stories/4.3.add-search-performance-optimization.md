## Story

**As a** backend developer,
**I want** to optimize search queries with composite indexes, query tuning, and caching,
**so that** metadata-enriched searches maintain sub-500ms response time at scale.

    ```python
    """
    Search Performance Benchmark Script

    Executes 100 search queries with various filter combinations and measures:
    - P95 latency (target: <500ms)
    - Average latency (target: <300ms)
    - Memory usage delta (target: <20% increase)

    Usage:
        uv run python -m scripts.benchmark_search_performance
    """
    import asyncio
    import time
    import statistics
    import tracemalloc
    from typing import Any

    # Query variations for comprehensive benchmarking
    BENCHMARK_QUERIES = [
        # Basic searches (no filters)
        {"query": "API documentation", "filters": None},
        {"query": "error handling", "filters": None},
        {"query": "configuration settings", "filters": None},

        # Space filter searches
        {"query": "deployment guide", "filters": {"space_key": "DEVDOCS"}},
        {"query": "architecture", "filters": {"space_key": "INTERNAL"}},

        # JIRA filter searches
        {"query": "bug fix", "filters": {"jira_issue": "PROJ-123"}},

        # Combined filters
        {"query": "setup instructions", "filters": {"space_key": "DEVDOCS", "jira_issue": "PROJ-456"}},

        # Hierarchy filter
        {"query": "getting started", "filters": {"hierarchy_path": "/parent123/"}},
    ]

    async def run_benchmark():
        """Execute benchmark and report results."""
        # Start memory tracking
        tracemalloc.start()
        baseline_memory = tracemalloc.get_traced_memory()[0]

        latencies = []

        # Run 100 queries (cycle through BENCHMARK_QUERIES)
        for i in range(100):
            query_config = BENCHMARK_QUERIES[i % len(BENCHMARK_QUERIES)]

            start = time.perf_counter()
            # Execute search (implementation needed)
            await execute_search(query_config["query"], query_config["filters"])
            elapsed_ms = (time.perf_counter() - start) * 1000

            latencies.append(elapsed_ms)

        # Calculate metrics
        p95 = statistics.quantiles(latencies, n=20)[18]  # 95th percentile
        avg = statistics.mean(latencies)

        # Memory check
        current_memory = tracemalloc.get_traced_memory()[0]
        memory_delta_percent = ((current_memory - baseline_memory) / baseline_memory) * 100

        # Report results
        print(f"P95 Latency: {p95:.2f}ms (target: <500ms) {'✅' if p95 < 500 else '❌'}")
        print(f"Avg Latency: {avg:.2f}ms (target: <300ms) {'✅' if avg < 300 else '❌'}")
        print(f"Memory Delta: {memory_delta_percent:.1f}% (target: <20%) {'✅' if memory_delta_percent < 20 else '❌'}")

        tracemalloc.stop()
    ```

### Technical Design Decisions

**Why Composite Index `(space_key, page_id)` Instead of Separate Indexes?**
- **Query pattern**: Story 4.2 filters by `space_key` frequently; `page_id` used in IN clause
- **Index efficiency**: Composite index covers both filter and lookup in single index scan
- **Partial index**: `WHERE is_deleted = FALSE` reduces index size and maintenance cost

**Why Post-Processing Pagination Instead of Database-Level?**
- **Confluence filters**: Story 4.2's filters are applied in Python after metadata enrichment
- **Simpler implementation**: No PostgreSQL function changes required
- **Trade-off**: Full result set still loaded initially, but filtered before return
- **Future optimization**: If performance becomes issue, push pagination to database level

**Why ETag Caching on Search Results?**
- **Bandwidth reduction**: ~70% reduction for unchanged results (per ETag analysis)
- **Client optimization**: TanStack Query can skip state updates on 304
- **30s stale time**: Balances freshness with performance (matches `STALE_TIMES.normal`)

**Why 1s Threshold for Slow Query Logging?**
- **Target P95**: <500ms, so 1s = 2x acceptable latency
- **Avoid noise**: Logging every query would be too verbose
- **Investigation trigger**: Slow queries indicate optimization opportunities
